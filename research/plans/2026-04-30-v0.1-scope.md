# Pauli Propagation Library — Design Document

## 1. Overview and Goals

This document specifies the design of a Rust library for Pauli propagation, with first-class Python bindings. The library targets classical simulation of quantum systems by evolving operators in the Pauli basis under the action of gates and noise channels — a technique applicable to Heisenberg-picture observable backpropagation, forward density-matrix-style evolution, and hybrid use cases such as operator backpropagation for error mitigation.

The design prioritizes four properties, in order:

1. **Correctness and clarity of the core algebra.** Pauli string manipulation is the foundation; bugs at this level invalidate everything downstream.
2. **Performance at scale.** The library must handle Pauli sums with millions to hundreds of millions of terms efficiently. Memory layout, cache behavior, and parallelism are first-class concerns.
3. **Extensibility for research.** Custom gates, custom noise channels, and custom truncation strategies must be implementable without forking the library.
4. **GPU-readiness.** A future GPU backend should be addable without restructuring the core data types or algorithms.

### Non-Goals

The library is not a state-vector simulator. It does not produce amplitudes for individual computational basis states. It does not implement tensor-network methods, stabilizer-formalism Clifford simulation, or matrix-product-state evolution. Pauli propagation is its own technique with its own scaling regime, and conflating it with adjacent methods would compromise the design.

The library does not aim to be a complete quantum SDK. It does not implement circuit compilation, transpilation, hardware-aware optimization, or pulse-level control. It expects circuits as input from upstream tooling such as Qiskit.

## 2. Crate Structure

The implementation is a Cargo workspace:

- `paulistrings` is the pure Rust library containing all algorithms and data types. It has no Python dependency. This crate is independently usable from other Rust projects and forms the basis for benchmarks and future GPU work. Criterion benchmarks live alongside the core crate at `crates/paulistrings/benches/`, run via `cargo bench -p paulistrings`. They benchmark against the released API surface, not internals.
- `paulistrings-py` contains the PyO3 bindings, built as a `cdylib` named `_paulistrings`. It is a thin wrapper that exposes the core types to Python, handles ergonomic conversions, and dispatches across the monomorphized width parameter (see Section 4).

A future GPU backend is anticipated as `paulistrings-gpu`, a sibling to the core crate that depends on it for shared types and traits but provides its own implementations of the parallel engine and channel applications.

## 3. Core Data Types

### 3.1 PauliString

A Pauli string is represented in the symplectic encoding: each qubit's Pauli operator is encoded as a pair of bits, with `I = (0,0)`, `X = (1,0)`, `Z = (0,1)`, `Y = (1,1)`. Multiplication of two Pauli strings is then bitwise XOR of their `(x, z)` parts, plus a phase factor `i^k` (for `k` in `0..4`) that arises when X-bits and Z-bits coincide.

The type is parameterized by a const generic `W` giving the number of `u64` words used to store each of the X-part and Z-part. A single word covers 64 qubits; four words cover 256, and so on. This monomorphization is essential for performance — it eliminates indirection, allows the compiler to unroll bit operations, and makes the type `Copy`, which matters because Pauli strings are passed by value throughout the algorithms.

```rust
#[derive(Clone, Copy, PartialEq, Eq, Pod, Zeroable)]
#[repr(C)]
pub struct PauliString<const W: usize> {
    x: [u64; W],
    z: [u64; W],
}
```

The `#[repr(C)]` attribute ensures a stable, ABI-defined layout; with two `[u64; W]` fields and no other members, the layout is `2 * 8 * W` bytes with no padding. The `Pod` and `Zeroable` derivations from `bytemuck` permit safe reinterpretation as bytes for serialization and for upload to GPU device memory in a future backend.

The load-bearing trait on `PauliString` is `Ord`, not `Hash`. This is a consequence of the algorithmic choice in Section 5: the engine relies on sorted representations rather than hashed ones. The `Ord` implementation must be cheap and well-defined; we adopt lexicographic comparison on the concatenation of `(x, z)` interpreted as unsigned-integer arrays, with a canonical low-to-high word ordering. Hashing is still implemented for use in auxiliary contexts (the `BuildAccumulator` of Section 8.2) but is not on the hot path.

There is no stored phase. The symplectic multiplication algebra produces a phase `k` in `0..4`; this is returned by `mul_assign` (and the value-returning `mul`) as a separate `u8`, and callers fold it into the relevant `Complex64` coefficient at the boundary — typically the moment a string is inserted into a `PauliSum` or `BuildAccumulator`. Storing phase on every standalone string would cost a byte (plus padding to maintain alignment) in memory and in the GPU buffer for a value that is, by `PauliSum`'s phase-zero invariant, zero anywhere it would be read in bulk.

### 3.2 PauliSum

A `PauliSum<W>` is a weighted sum of Pauli strings — the central data structure of the library. Its canonical form is a structure-of-arrays layout, sorted by Pauli key with no duplicates:

```rust
pub struct PauliSum<const W: usize> {
    x: Vec<[u64; W]>,
    z: Vec<[u64; W]>,
    coeff: Vec<Complex64>,
    num_qubits: usize,
}
```

The invariant maintained by every operation is that the parallel arrays `x` and `z` are sorted in lexicographic order as a single key, and that no two entries share a key. This invariant is what makes the sort-merge algorithm of Section 5 work, and it makes a wide range of bulk operations efficient: scanning for a particular Pauli is a binary search, summing two `PauliSum`s is a linear merge, and every per-term operation is trivially parallelizable because there is no shared mutable state.

The structure-of-arrays layout is chosen over array-of-structures for two reasons. First, many algorithms touch only the coefficients (truncation by magnitude, expectation value computation) or only the keys (commutation analysis, weight computation), and SoA gives perfect cache utilization for these scans. Second, this layout maps directly to GPU memory: each `Vec` becomes a device buffer with no marshaling.

## 4. Width Monomorphization

The const generic `W` is a compile-time parameter, but Python users provide `num_qubits` at runtime. The Python boundary therefore monomorphizes at a fixed set of widths covering common qubit counts (e.g. 1, 2, 4, 8, 16 corresponding to 64, 128, 256, 512, 1024 qubits) and dispatches based on the smallest width that fits the user's circuit:

```rust
enum PauliSumImpl {
    W1(PauliSum<1>),
    W2(PauliSum<2>),
    W4(PauliSum<4>),
    W8(PauliSum<8>),
    W16(PauliSum<16>),
}
```

This trades binary size for performance — the engine is monomorphized for each width, allowing the compiler to fully unroll bit operations. The runtime cost is a single match dispatch per top-level operation, which is outside any hot loop.

Users who need wider Pauli strings or who want to avoid the binary-size cost can use the core crate directly from Rust with their own choice of `W`.

## 5. Algorithmic Approach: Sort-Merge

The central algorithmic decision of this library is to use sort-and-merge as the primary aggregation strategy, rather than hashmap-based deduplication. This decision is grounded in a structural observation about the workload.

When a channel acts on a Pauli string, it touches only the qubits in its support. For a single-qubit gate, that is one qubit; for a two-qubit gate, two; for typical noise channels, similarly few. The output Pauli strings differ from their inputs only at those bit positions. If the input sum is sorted by Pauli key, the output sum after gate application is *almost sorted*: ordering is preserved across all bit positions outside the gate's support, and is perturbed only at the few positions inside it.

This structure is incompatible with hashmap-based merging, which treats every output as an independent insertion and pays the full hash-and-probe cost regardless of locality. It is, however, ideal for bucket-based sorting: the perturbed bits define a small fixed set of buckets (sixteen for a two-qubit gate, four for a single-qubit gate), and within each bucket the relative order of inputs is preserved. Sorting therefore reduces to a single linear-time bucket assignment followed by concatenation.

The propagation loop becomes a three-phase pipeline applied per channel:

**Scan phase.** For each input term, the channel computes its outputs. Each input produces at most `MAX_FANOUT` output terms (a per-channel constant, typically 1, 2, or 4). Outputs are written into a pre-allocated buffer of size `n_in × MAX_FANOUT`. This phase is purely data-parallel with no synchronization.

**Bucket phase.** The output buffer is partitioned into `2^(2|support|)` buckets indexed by the bits at the channel's support qubits. Within each bucket the relative order is inherited from the input. The bucket count is known at compile time per channel kind.

**Merge phase.** Adjacent terms with identical Pauli keys are combined by summing their coefficients. This is a segmented reduction over the sorted output, expressible as a single linear pass on CPU or as a CUB-style segmented prefix-scan on GPU. Truncation is folded into this pass: terms whose merged coefficient falls below the truncation threshold, or whose weight exceeds the cutoff, are omitted from the output.

The result is a fully sorted, deduplicated, truncated `PauliSum` ready for the next channel.

This algorithm has the additional property that CPU and GPU implementations are structurally identical. The same three phases run on both architectures; only the mechanics of parallelism differ. CPU uses Rayon parallel iterators with chunked scans and segment-aware merges; GPU uses kernel launches with CUB primitives. The `Channel::apply` method body — the per-term work — is shared logic.

## 6. Channel Trait

The `Channel` trait abstracts every operation that acts on a Pauli sum: Clifford gates, Pauli rotations, arbitrary unitaries (decomposed into Pauli expansions at construction time), and noise channels. The unifying observation is that, in the Heisenberg picture, every such operation maps a single Pauli string to a small weighted sum of Pauli strings.

```rust
pub trait Channel<const W: usize>: Send + Sync {
    /// Qubits this channel acts on. Outputs differ from inputs only here.
    fn support(&self) -> &[u32];

    /// Maximum number of output terms per input term.
    const MAX_FANOUT: usize;

    /// Apply the channel to a single input term, writing outputs to `out`.
    fn apply(
        &self,
        input_x: &[u64; W],
        input_z: &[u64; W],
        coeff: Complex64,
        out: &mut OutputBuffer<W>,
    );
}
```

The `support` method is consulted by the engine to determine bucket layout for the sort-merge pipeline. The `MAX_FANOUT` associated constant is consulted to size output buffers without dynamic growth — this matters both for CPU performance (avoiding heap allocation in the hot loop) and for GPU correctness (kernels cannot grow buffers).

Built-in channel implementations cover the standard cases: `Clifford1Q` and `Clifford2Q` for Clifford gates (table-driven from their symplectic matrices, branchless), `PauliRotation` for `exp(-iθP/2)` rotations, `GeneralUnitary1Q` and `GeneralUnitary2Q` for arbitrary unitaries pre-decomposed into Pauli expansions, and noise channels `Depolarizing`, `Dephasing`, and `AmplitudeDamping`. The first two noise channels reduce to coefficient rescaling based on Pauli support, which makes them especially fast; amplitude damping genuinely produces multiple output terms per input.

Custom channels are implemented by users by implementing the trait. This is the primary research extensibility surface for novel gate sets, exotic noise models, or learned channels.

## 7. Truncation Policies

Truncation is the primary mechanism by which Pauli propagation remains tractable on hard problems, and the library exposes it as a composable, extensible system.

```rust
pub trait TruncationPolicy<const W: usize>: Send + Sync {
    /// Cheap per-term filter applied during the merge phase.
    #[inline]
    fn keep_term(&self, x: &[u64; W], z: &[u64; W], c: Complex64) -> bool {
        true
    }

    /// Optional global pass after each layer.
    fn finalize_layer(&self, sum: &mut PauliSum<W>) {}
}
```

The two-method split is performance-critical. The `keep_term` filter is called on every output of every channel application — potentially billions of times in a deep simulation — and must inline and execute in nanoseconds. The `finalize_layer` hook is called once per circuit layer and may perform non-local operations such as keeping only the top-N terms by magnitude.

The library ships three built-in policies covering the standard knobs: `CoefficientThreshold(epsilon)` drops terms below an absolute coefficient magnitude; `WeightCutoff(k)` drops terms whose Pauli weight (number of non-identity qubits) exceeds `k`; `TopN(n)` retains only the `n` terms with largest coefficient magnitude after each layer. The first two are per-term filters; the third is a layer finalization.

Policies compose via `And` and `Or` combinators, both at the Rust level and exposed through Python operator overloads (`&` and `|`). A typical research configuration might be `CoefficientThreshold(1e-10) & WeightCutoff(8) & TopN(1_000_000)`.

Custom policies are first-class: implementing the trait gives users full control over which terms survive each layer. This is the second major research extensibility surface.

## 8. Engine and Propagation Loop

### 8.1 The Main Loop

Propagation iterates over the channels in a circuit, applying each to the current `PauliSum` to produce the next. Direction (forward versus Heisenberg) is a parameter of the top-level call; in Heisenberg mode the channels are iterated in reverse and their adjoints applied.

```rust
pub fn propagate<W: usize, T: TruncationPolicy<W>>(
    circuit: &Circuit<W>,
    initial: PauliSum<W>,
    policy: &T,
    direction: Direction,
) -> PauliSum<W>
```

Each layer execution is the three-phase scan-bucket-merge pipeline of Section 5, with truncation woven into the merge phase via `policy.keep_term`, followed by a call to `policy.finalize_layer` if any global truncation is required.

### 8.2 BuildAccumulator

For ingesting unsorted input — parsing a Hamiltonian from a file, constructing a `PauliSum` from a Python dictionary, accumulating terms during a custom analysis — a `BuildAccumulator` provides hashmap-based incremental insertion. Its `finalize` method produces a sorted, deduplicated `PauliSum`.

```rust
pub struct BuildAccumulator<const W: usize> {
    map: hashbrown::HashMap<PauliString<W>, Complex64, FxBuildHasher>,
}

impl<const W: usize> BuildAccumulator<W> {
    pub fn add_term(&mut self, p: PauliString<W>, c: Complex64);
    pub fn finalize(self) -> PauliSum<W>;
}
```

The accumulator uses `FxBuildHasher` rather than the default hasher because Pauli bitstrings are already high-entropy, and the cryptographic strength of SipHash is unnecessary for this distribution. A multiply-shift hash is several times faster.

The accumulator is not used during propagation. It exists solely as an ingestion path.

### 8.3 Small-Sum Fast Path

For very small Pauli sums (under a few thousand terms), the constant-factor overhead of bucket sorting and segmented reduction can exceed the cost of a single hashmap pass. The engine includes a tunable threshold below which it falls back to direct hashmap-style merging within a single layer. The crossover is an implementation detail and is determined empirically; the public API is unaffected.

## 9. Parallelism

CPU parallelism is implemented via Rayon. The scan phase is a parallel iterator over the input `PauliSum`, with each thread writing its outputs to a thread-local output region of the pre-allocated buffer. The bucket phase parallelizes across buckets — each bucket's contents are independent. The merge phase uses a chunked segment-aware reduction: the buffer is partitioned into chunks, each thread merges within its chunk, and a final pass reconciles segment boundaries.

This pattern keeps all parallelism shared-nothing. There is no concurrent hashmap, no dynamic load balancing within a phase, and no synchronization beyond the phase boundaries. The result is near-linear scaling up to the memory bandwidth limit.

## 10. GPU Readiness

The architecture admits a GPU backend without restructuring the core. The relevant design decisions are already in place: `PauliString<W>` is `Pod` and uploadable; `PauliSum<W>` is structure-of-arrays and maps directly to device buffers; channels declare `MAX_FANOUT` so output buffers can be pre-sized; the sort-merge algorithm is the same on both architectures.

A future `paulistrings-gpu` crate would depend on `paulistrings` for the type definitions and the `Channel` and `TruncationPolicy` traits, and would provide its own engine implementation using CUDA via `cust` or `cudarc`. Channel implementations for the GPU would be separate types that share data tables (Clifford symplectic matrices, rotation angle parameters) with their CPU counterparts.

The realistic scope of an initial GPU backend is the standard channel set (Clifford, Pauli rotation, depolarizing, dephasing) over the sort-merge engine. Arbitrary unitaries and amplitude damping are tractable but require more careful kernel design. Truncation policies that are kernel-compilable (coefficient threshold, weight cutoff) work directly; `TopN` requires a device-side partial sort and is implementable but non-trivial.

GPU is not expected to dominate uniformly. It wins on wide-and-shallow circuits and low-collision regimes; it loses on small problems where transfer dominates and on heavily-truncating workloads where CPU's branchy code is more efficient. The library will support both backends and let users select based on their workload.

## 11. Python Bindings

The Python API is a thin layer over the monomorphized `PauliSumImpl` enum. The user-visible surface is a small set of classes — `PauliSum`, `Circuit`, channel factories, truncation factories — that hide the width dispatch entirely.

```python
from paulistrings import PauliSum, Circuit, gates, noise, truncation

obs = PauliSum.from_strings({"ZZIII...": 1.0}, num_qubits=20)

c = Circuit(num_qubits=20)
c.h(0)
c.cnot(0, 1)
c.rz(0.5, 1)
c.depolarize(0.01, qubits=[0, 1])

policy = truncation.coeff(1e-10) & truncation.weight(8)
result = obs.propagate(c, policy=policy, direction="heisenberg")
```

Construction methods accept the natural Python forms — dictionaries keyed by Pauli strings, lists of `(string, coefficient)` tuples, and NumPy arrays for bulk loading. The bit-encoded representation is hidden; users do not interact with X-parts or Z-parts directly.

NumPy interop is supported at the boundaries: initial states and final expectation-value computations accept and return NumPy arrays. The bulk SoA storage is exposed as zero-copy NumPy views for advanced users who want to operate on the raw representation.

## 12. Open Questions

A handful of decisions remain open and will be settled during implementation:

The exact crossover threshold between sort-merge and hashmap-based merging in the small-sum fast path is empirical. It will be determined by benchmarking and may be exposed as a tunable parameter.

The bucket sort in the bucket phase has multiple reasonable implementations (in-place partition, out-of-place scatter, two-pass count-and-place). The choice depends on cache behavior at scale and will be determined by benchmarking against representative workloads.

The set of monomorphized widths in the Python boundary is currently planned as `{1, 2, 4, 8, 16}`. Whether to extend to 32 (2048 qubits) or to allow runtime extension via a heap-allocated fallback is an open question depending on user demand.

Whether to support distributed-memory parallelism (MPI, multi-node) is an open architectural question. The sort-merge algorithm extends naturally to distributed execution via a partitioning scheme on the high-order key bits, but the engineering cost is substantial and depends on whether users have problems large enough to justify it.

## 13. Implementation Plan

The implementation proceeds bottom-up, with each module fully tested before the next is built:

1. `PauliString<W>`: encoding, multiplication (returning the `i^k` phase as a `u8`), commutation, weight, lexicographic comparison. The foundation; everything else depends on its correctness.
2. `PauliSum<W>`: SoA storage, sorted invariant, construction from `BuildAccumulator`, basic operations (sum, scalar multiplication, equality).
3. `Channel` trait and built-in Clifford and Pauli rotation implementations. At this point, single-channel application is functional end-to-end.
4. The sort-merge engine: scan, bucket, merge phases, with single-threaded execution first.
5. Rayon parallelization of the engine.
6. `TruncationPolicy` trait and built-in policies, integrated into the merge phase.
7. Noise channels: `Depolarizing`, `Dephasing`, `AmplitudeDamping`.
8. PyO3 bindings, width monomorphization dispatch, NumPy interop.
9. Benchmarks, profiling, optimization pass.

GPU backend work is deferred until the CPU library is feature-complete and validated against known reference implementations.
