# v0.2 — GF(2)-linear bucketing engine

*2026-08-26. Supersedes `2026-04-30-v0.1-scope.md` §5 (Algorithmic Approach) and
§9 (Parallelism). Every other section of the v0.1 scope doc — §1 goals, §3 core
data types, §4 width monomorphization, §6 channel trait, §7 truncation, §8.1/8.2
propagation and ingestion, §10 GPU readiness, §11 Python bindings — remains in
force and is referenced here by its original number.*

---

## 1. Why

v0.1's engine is `scan → sort → merge`. The scan and merge are Rayon-parallel;
the sort is not, and it is the whole cost (`engine/sort_merge.rs:215`): a
sequential, stable, indirect-comparator `O(n log n)` sort followed by a second
full materialization of the payload. The design doc's intended replacement — the
`O(n)` bucket phase of §5 — rests on a false ordering claim and was never
implemented; `Channel::support()`, added solely to feed it, has never been called
by the engine. See `research/notes/2026-08-26-why-s5-concatenation-fails.md` for
the counterexample and the two ways out.

v0.2 takes the second way out: **stop maintaining one global sorted order.**
Partition the sum with a GF(2)-linear hash instead. The partition is persistent
across layers, commutes with gate action in a way that makes output buckets
predictable, and makes deduplication bucket-local — so there is no global sort
anywhere in the algorithm.

Beyond the sort, v0.1 pays per channel application: ~11 + 3k allocations (none
reused across layers, three of them zero-filled at `n × MAX_FANOUT`), ~4 full
passes over the payload, a vtable call per input term (`Circuit` stores
`Box<dyn Channel<W>>`, so nothing devirtualizes), and per-term work that belongs
once per layer — `PauliRotation::apply` recomputes `theta.cos()/sin()` for every
term (`rotation.rs:45`); `Clifford1Q::apply_adjoint` rebuilds its inverse table
for every term (`clifford.rs:168`).

Two of those are now measured, and the measurement matters for how they are
weighted (`research/notes/2026-08-26-v0.1-baselines-extended.md`):

- **The per-term vtable call costs 1–3% at n = 10⁶** — at or barely above the
  noise floor. It is *not* a source of speedup; it merely comes free with the
  prepared form of §5. Do not claim otherwise.
- **Layer cost is independent of the channel.** At n = 10⁶, `Depolarizing`
  (60.8 ms), `Clifford1Q::h` (60.3 ms) and `Clifford2Q::cnot` (61.2 ms) are
  identical within noise, against 19.0 ms for `PauliSum::add` over a comparable
  payload. A `Depolarizing` layer leaves every key bitwise unchanged — its output
  is *already* sorted and duplicate-free — and still costs what a two-qubit
  Clifford conjugation costs. The channel's own work is not measurable; the layer
  is the engine.

That second point is the real justification for this redesign, and it is why
whole channel classes paying for nothing (`Depolarizing`, `Dephasing`,
`Clifford1Q::{x,y,z}`, `IdentityChannel` — all key-preserving) is not a corner
case but the common one.

Priorities are unchanged from §1: correctness first, then performance at
10⁶–10⁸ terms, then research extensibility, then GPU-readiness.

## 2. The GF(2) algebra

### 2.1 Keys form a vector space; multiplication is XOR

Under §3.1's symplectic encoding a Pauli string is `v = (x, z) ∈ GF(2)^{2n}`, and
`mul_assign` (`pauli_string.rs:179`) does `x ^= x'; z ^= z'`, returning only the
`i^k` phase. The key space is therefore a GF(2) vector space under `⊕`, and the
phase — which §3.1 already keeps out of the key — stays out of this section
entirely.

### 2.2 The bucket function

Fix a matrix `H ∈ GF(2)^{b × 2n}` and define

```
h(v) = H·v  ∈ GF(2)^b,        B = 2^b buckets.
```

Linearity gives the single property everything below follows from:

```
h(v ⊕ d) = h(v) ⊕ h(d)                                                (★)
```

### 2.3 Channels act by a bounded delta set

A channel with support `S`, `|S| = k`, maps an input key to outputs differing
only inside the `2k` support coordinates:

```
v_out = v ⊕ d,        d ∈ D ⊆ V_S ≅ GF(2)^{2k}.
```

`D` is the channel's **delta set**. For every channel in v0.1's built-in set `D`
is in fact a *linear subspace*. For a Clifford the symplectic map is `v ↦ Sv`, so
`d = (S ⊕ I)v` and `D = im(S ⊕ I)`, an image and hence a subspace. Verified
against the shipped tables (packing `idx = x | (z << 1)`, i.e. `I,X,Z,Y = 0,1,2,3`):

| channel | table / action | `D` | `dim D` |
|---|---|---|---|
| `IdentityChannel` | — | `{0}` | 0 |
| `Depolarizing`, `Dephasing` | keys unchanged, coeff rescaled | `{0}` | 0 |
| `Clifford1Q::{x,y,z}` | `out_pauli = [0,1,2,3]` (identity perm) | `{0}` | 0 |
| `Clifford1Q::h` | `[0,2,1,3]`: `1↔2` | `{0, (x⊕z)}` | 1 |
| `Clifford1Q::s` | `[0,3,2,1]`: `1↔3` | `{0, e_z}` | 1 |
| `PauliRotation(Q)`, **any weight** | second output is `v ⊕ q` | `{0, q}` | 1 |
| `AmplitudeDamping` | `Z ↦ (1-γ)Z + γI` | `{0, e_z}` | 1 |
| `Clifford2Q::cnot` | `d = (0, z₁, x₀, 0)` | 2-dim | 2 |
| `Clifford2Q::cz` | `d = (0, x₁, 0, x₀)` | 2-dim | 2 |
| `Clifford2Q::swap` | `d = (x₀⊕x₁, z₀⊕z₁, x₀⊕x₁, z₀⊕z₁)` | 2-dim | 2 |
| `GeneralUnitary1Q` | full local PTM | `V_S` | 2 |
| `GeneralUnitary2Q` | full local PTM | `V_S` | 4 |

### 2.4 Bucket prediction, and its inverse

Combining (★) with §2.3:

```
forward:   h(v_out) ∈ h(v_in) ⊕ h(D)
inverse:   the inputs contributing to output bucket β′ live in  β′ ⊕ h(D)
```

`h(D)` is a linear subspace of `GF(2)^b` of dimension `r = rank(H|_D) ≤ dim D`,
so the inverse set is an **affine subspace of exactly `2^r` buckets**. Because
`⊕` is an involution, forward and inverse fan-out are the same number:

| channel | input buckets read per output bucket |
|---|---|
| identity, depolarizing, dephasing, Pauli gates | **1** |
| Pauli rotation (any generator weight), amplitude damping, `H`, `S` | **2** |
| `CNOT`, `CZ`, `SWAP`, `GeneralUnitary1Q` | **4** |
| `GeneralUnitary2Q` | **16** |

This is the load-bearing structural fact. **Each output bucket reads a
statically-known handful of input buckets and writes nowhere else.** Output
buckets are write-disjoint, so the parallel decomposition has one owner per
bucket: no atomics, no concurrent hashmap, no cross-thread reconciliation, and
none of v0.1's `align_chunk_boundaries` serial boundary scan.

Note the rotation row: `dim D = 1` **regardless of generator weight**, because
the delta is the fixed vector `q`. Under the support-derived bucketing §5
envisaged, a weight-`w` rotation would have needed `4^w` buckets; here it needs 2.
Every channel in `examples/ising_2d_quench.rs` is a rotation.

### 2.5 Dedup becomes bucket-local — the global sort disappears

`h` is a function, so `v = w ⇒ h(v) = h(w)`. **Duplicate keys can never straddle
buckets.** Deduplication therefore only ever needs a canonical order *within* a
bucket, and the propagation invariant weakens from §3.2's "sorted by the
concatenated `(x,z)` key, no duplicates" to "partitioned by `h`, sorted by
`(x,z)` within each part". Nothing in the algorithm requires a global sort.

This is also what generalises §8.3. The small-sum hashmap fast path was scoped as
a special case for `n` below a few thousand; under a bucket partition **every
bucket is a small sum**, so an L1-resident dedup is available at any `n` (§7.3).

### 2.6 The per-(input, output) bucket delta is a constant

Filling output bucket `β′` from input bucket `β = β′ ⊕ δ` requires `d ∈ D` with
`H d = δ`. When `rank(H|_D) = dim D` — generic for random `H`, §3.2 — that `d` is
**unique and independent of the term**. The inner loop is therefore:

```rust
// δ, d, mask_x, mask_z, amp all fixed for this (input bucket, output bucket) pair
for t in in_bucket[β_prime ^ delta] {
    let a = amp[support_bits(t)];        // ≤4 bits extracted; i^k already baked in
    if a != ZERO {
        push(t.x ^ mask_x, t.z ^ mask_z, t.coeff * a);
    }
}
```

One table lookup on ≤4 extracted bits, one XOR with a precomputed mask, one
complex multiply. No dynamic dispatch, no `sin`/`cos`, no `mul_assign` popcounts,
no `Phase` arithmetic, no `OutputBuffer`, and no `MAX_FANOUT`-sized scratch per
input term.

When `rank(H|_D) < dim D`, several `d` share a `δ`; each `δ` then has exactly
`2^{dim D − r}` preimages, handled by iterating a short member list per `δ`.
**Correctness never depends on `H` being well-chosen — only performance does.**

### 2.7 Bucket refinement is one parity pass

Take `H`'s rows as a *prefix* of a fixed random `H_max ∈ GF(2)^{b_max × 2n}`.
Then `h_{b+1}(v) = (h_b(v), row_{b+1}·v)`, so `B → 2B` **splits each bucket in
two**, and the within-bucket order is inherited by both halves — an `O(n)` parity
pass with no re-sorting. `B → B/2` merges bucket pairs with a 2-way merge. Since
`n` swings by orders of magnitude across a run (fanout grows it, truncation cuts
it back), this incremental rehash is what makes a *persistent* partition viable.

## 3. `Gf2Hash<W>`

### 3.1 Representation

```rust
pub struct Gf2Hash<const W: usize> {
    rows_x: Vec<[u64; W]>,   // b_max rows; columns beyond num_qubits masked to 0
    rows_z: Vec<[u64; W]>,
    b: u8,                   // active prefix length; B = 1 << b
    seed: u64,
}
```

`bucket_of(x, z)` sets bit `i` of the result to
`parity(x & rows_x[i]) ^ parity(z & rows_z[i])` — `b × 2W` AND + popcount-parity
operations. Rows are generated from `seed` by the same xorshift64 construction
already used for deterministic bench input (`benches/pauli_ops.rs:33-57`), so `H`
is reproducible without adding a dependency. Columns outside `2·num_qubits` are
masked to zero at construction, both so the uniformity argument applies to the
live coordinate space and so `assert_invariants`' `is_within` contract is not
silently relied upon.

`H` is stored with the sum: two `BucketedSum`s can only be combined if they share
it. At `b_max = 20, W = 16` it is 5 KB.

### 3.2 Why dense and random

A coordinate projection (bucket = some chosen key bits) is GF(2)-linear too, and
has the appealing property that `h(D) = {0}` for a gate acting far from the
chosen coordinates — every output stays in its own bucket. It is nevertheless the
wrong choice: `WeightCutoff` truncation keeps sums *low-weight*, so the chosen
coordinates are almost always `0` and essentially everything lands in bucket 0.
Load balance would collapse exactly on the workloads we care about.

A dense random `H` is a universal (linear) hash family on `GF(2)^{2n}`: for `m`
distinct keys the maximum bucket load is `m/B + O(√(m log B / B))` with high
probability, *independent of the input's structure*. It also gives
`rank(H|_D) = dim D` with probability `≥ 1 − 2^{dim D − b}`, so §2.6's
"one constant `d` per bucket pair" is the overwhelmingly common case.

The cost — `b × 2W` popcounts per term — is paid **only at ingestion and at
rehash, never in the propagation loop** (§2.6). Known wart: `h(0) = 0`, so the
identity string always lands in bucket 0. One term; ignored.

## 4. `BucketedSum<W>`

### 4.1 Relation to `PauliSum<W>`

`PauliSum<W>` is **unchanged**: §3.2's invariant, `assert_invariants`, `add`,
`find`, `scale`, `truncate_by_magnitude`, the SoA accessors and the NumPy layout
all stay exactly as they are. It remains the public, canonical, globally-sorted,
GPU-uploadable type. `BucketedSum<W>` is the *propagation working form*:

```
propagate:  PauliSum --from_sum--> BucketedSum --(N layers)--> BucketedSum --into_sum--> PauliSum
```

Conversion in is `O(n)` hash + scatter; conversion out is a `B`-way merge at
`O(n log B)`. Both are paid once per `propagate` call, amortized over every layer
in the circuit — 4320 of them for a single 6×6 Ising quench.

### 4.2 Representation

```rust
pub struct BucketedSum<const W: usize> {
    buckets: Vec<BucketCols<W>>,   // len == 1 << hash.b
    hash: Gf2Hash<W>,
    num_qubits: usize,
    len: usize,                    // cached total
}
struct BucketCols<const W: usize> {
    x: Vec<[u64; W]>, z: Vec<[u64; W]>, coeff: Vec<Complex64>,
}
```

**Invariant:** every term lies in `buckets[hash.bucket_of(term)]`, and each
bucket is sorted by lex `(x, z)` with no duplicate keys. Note this *implies*
global dedup, by §2.5.

Per-bucket owned columns, rather than one flat SoA plus offsets, because
**capacity is retained across layers**. That alone removes essentially all of
v0.1's ~11 + 3k allocations per layer, which matters more than cross-bucket
contiguity when the parallel unit *is* the bucket. This is a deliberate departure
from §3.2's "each `Vec` maps directly to a GPU device buffer"; a flat form is
recoverable in a single pass, and §10 revisits it.

Within-bucket sortedness is kept (rather than relying on hashmap dedup alone)
because it makes `into_sum` a merge instead of a sort, makes the §2.7 refine
split order-preserving for free, and keeps `add`-style two-pointer merges
available per bucket.

### 4.3 Bucket-count policy

Target a bucket that fits comfortably in L2 alongside its scratch. On the
reference machine (Xeon Gold 6244, **1 MiB L2 per core**, 49.5 MB L3, 2 NUMA
nodes) a term at `W=2` is 48 B, so 1024 terms is ~48 KB — L2-resident with room
for the gather scratch and the sort permutation.

```
b = clamp(ceil(log2(n / TARGET_BUCKET_LEN)), ceil(log2(4 * threads)), B_MAX_BITS)
```

with `TARGET_BUCKET_LEN = 1024`, `B_MAX_BITS = 20`. The lower bound keeps at
least ~4 buckets per thread so the bucket-parallel decomposition has slack to
load-balance. Rehash only when out of band — refine above `4 ×` target, coarsen
below `¼ ×` — so the swings in `n` that `finalize_layer` causes every layer do
not thrash `rebucket`. All three constants are guesses until §7.4 measures them.

## 5. Prepared channels

### 5.1 The prepared form

Built once per layer, consumed by the engine:

```rust
pub enum Prepared<const W: usize> {
    /// Amplitudes depend only on the ≤4 support bits. Covers Clifford1Q/2Q, all
    /// noise channels, GeneralUnitary1Q/2Q, and PauliRotation at generator
    /// weight ≤ 2.
    Local { qubits: SmallVec<[u32; 2]>, k: u8, groups: Vec<DeltaGroup<W>> },
    /// D = {0, gen} at arbitrary generator weight; amplitude from a
    /// symplectic-parity bit rather than a table.
    Rotation {
        gen: PauliString<W>, live_words: SmallVec<[usize; 2]>,
        cos: f64, sin: f64, groups: [DeltaGroup<W>; 2],
    },
}

pub struct DeltaGroup<const W: usize> {
    pub bucket_delta: u32,                      // δ = H·d, shared by all members
    pub members: SmallVec<[DeltaEntry<W>; 1]>,  // len > 1 only on a hash collision
}

pub struct DeltaEntry<const W: usize> {
    pub mask_x: [u64; W], pub mask_z: [u64; W], // d, as full-key XOR masks
    pub amp: [Complex64; 16],                   // indexed by support bits s; 0 = no output
}
```

`4^k ≤ 16` amplitudes × ≤16 entries = 4 KB per layer. The `i^k` phase is folded
into `amp` at prepare time, which is what removes `Phase` arithmetic from the hot
loop.

Two channel classes get special handling in the engine rather than a new variant:
a `Local` whose single group has a single member with `mask == 0` (identity,
depolarizing, dephasing, Pauli gates) is an in-place coefficient rescale — no
gather, no sort, no merge.

### 5.2 The `Channel` trait gains one method, with a free default

§6's trait keeps `apply`, `apply_adjoint`, `support` and `max_fanout` unchanged.
`support()` finally becomes load-bearing rather than dead code, as §6 line 130
always intended. Added:

```rust
fn prepare(&self, hash: &Gf2Hash<W>, adjoint: bool) -> Prepared<W> {
    Prepared::derive_local(self, hash, adjoint)
}
```

**The default implementation is automatic and complete for any channel with
`|support| ≤ 2`.** `derive_local` calls the channel's own `apply` on each of the
`4^k ≤ 16` local basis Paulis and reads the local Pauli-transfer matrix straight
off the results, then derives `D = { s ⊕ t : amp[s][t] ≠ 0 }` and groups it by
`H·d`. So §6's "primary research extensibility surface" does not grow at all: a
custom channel that implements `apply` gets the bucketed engine for free.

The derivation doubles as a cross-check between the two representations, which is
the mechanism §9 relies on.

Only channels with support on more than 2 qubits need to override — in v0.1's
built-in set, only `PauliRotation` at generator weight > 2.

### 5.3 The soundness precondition

`derive_local` is correct exactly when the channel honours the bounded-support
contract: **the output amplitude must depend on the input only through its
support bits.** A channel that declares `support = [0]` and then reads qubit 5
would produce a silently wrong table. This is now a documented trait requirement,
pinned by a property test that checks each derived table against `apply` on
randomized *full-width* inputs (§9).

Relatedly, `PauliRotation::support` is currently caller-supplied and never
validated against the generator's bits. Today that is benign; under any
support-derived bucketing it would become a silent miscompilation of sort order.
v0.2 derives the support from the generator and validates any supplied value.

### 5.4 `MAX_FANOUT` stops being an engine concern

§5 and §6 make `MAX_FANOUT` load-bearing for buffer sizing. Under §2.6 the gather
emits at most one output per (term, delta entry), and the scratch for an output
bucket is sized exactly from the lengths of the input buckets it reads — known
before any work begins. So there are no `n × MAX_FANOUT` zero-filled buffers, no
per-input `lens` vector, and no `compact_in_place` pass. `max_fanout` survives
only on the v0.1 oracle path.

## 6. The per-layer algorithm

For each output bucket `β′`, independently:

1. **Size.** `Σ_groups Σ_members |in_bucket[β′ ⊕ δ]|`. Exact, from bucket lengths,
   before any work. No over-allocation, no zero-fill.
2. **Gather.** For each delta entry in canonical order (§8), run §2.6's inner loop
   over `in_bucket[β′ ⊕ δ]`, appending to scratch. `keep_term` is *not* applied
   here — §7 requires it to see the summed coefficient.
3. **Sort.** Reuse v0.1's `sort_merge::sort_phase` on the scratch. Its sequential,
   stable, indirect-comparator character — the v0.1 bottleneck — is *correct* at
   this scale: parallelism now lives at the bucket level, and at ~1k terms the
   permutation indirection is L1-local. Only its three internal gather `Vec`s
   change, into pooled per-thread scratch.
4. **Merge.** Reuse `sort_merge::merge_chunk`'s body: segmented reduction of
   adjacent equal keys, exact-zero drop, `keep_term` on the summed coefficient.
   Its signature changes from "returns three `Vec`s" to "appends into three
   `&mut Vec`s", so it writes straight into the destination bucket instead of
   growing un-preallocated intermediates. `nchunks = 1` within a bucket, so
   `align_chunk_boundaries` is not involved.

Bucket storage is double-buffered front/back and swapped, so all capacity is
retained across layers.

The v0.1 whole-sum path is retained, both as the differential-testing oracle
(§9) and as the live fallback below a small-`n` threshold — which is the honest
version of §8.3's crossover.

## 7. Parallelism

Replaces §9.

v0.1 §9 claims this pattern yields "near-linear scaling up to the memory
bandwidth limit". Measured, one rotation layer at n = 10⁶ scales **1.32× from 1 to
16 threads, and regresses at 32** — a serial fraction of `s ≈ 0.74` by Amdahl.
Roughly three-quarters of a layer runs on one core. §9 is off by ~24×. See
`research/notes/2026-08-26-v0.1-baselines-extended.md` §2; that table is the
before-figure this section has to beat.

The parallel decomposition is **one output bucket per task**. By §2.4 a task
reads `2^r ≤ 16` input buckets and writes only its own, so:

- No atomics, no concurrent hashmap, no locks.
- No cross-thread reconciliation pass. v0.1's merge needed
  `align_chunk_boundaries` because a run of equal keys could straddle a chunk
  boundary; within a bucket partition, a run cannot straddle *anything* (§2.5).
- No synchronization inside a layer at all — only the layer boundary itself.

This is strictly stronger than §9's "shared-nothing" claim, which still had a
boundary-reconciliation pass and a sequential sort between its parallel phases.

Load balance comes from `H` (§3.2) plus `B ≥ 4 × threads` (§4.3), letting Rayon's
work-stealing absorb the residual Poisson variation in bucket occupancy. The
reference machine has 2 NUMA nodes, so first-touch placement of bucket storage is
a real consideration at 32 threads; §7.4 measures it rather than guessing.

### 7.1 – 7.4 Deferred to measurement

Enumerated so they are not silently skipped, and so no bound goes in unlogged:

**7.1 `Phase`-valued amplitude tables.** `Clifford::apply` currently does
`phase[idx].apply(coeff)` — a sign/swap with *no* floating-point multiply
(`phase.rs:80-88`). A `Complex64` amplitude always costs a full complex multiply,
so the table path of §2.6 is *slower per term* for pure Cliffords than what it
replaces. Add `Phase`-valued and `f64`-valued variants (the latter for the
real-amplitude noise channels) and measure.

**7.2 k-way run merge instead of a per-bucket sort.** Within a `(β, d)` pair the
delta is constant (§2.6), and XOR by a constant preserves integer order on any
set where the constant's bits agree. Partitioning an input bucket by the
`popcount(d)` delta bits therefore yields at most `2^popcount(d)` *sorted runs*,
mergeable at `O(m log k)`. For 1Q/2Q gates `popcount(d) ≤ 4`, so `log k ≤ 4`
against `log₂ 1024 = 10` for the sort. This is §5's bucket phase, finally on a
foundation where the ordering claim holds — but it degrades for high-weight
rotation generators (`popcount(d) = 2w`), so it must be conditional on
`popcount(d)`.

**7.3 L1 hashmap dedup per bucket instead of sort-then-reduce**, per §2.5. Needs
a fixed accumulation order to stay deterministic; emission order is free because
`into_sum` sorts regardless.

**7.4 Constants and placement.** `TARGET_BUCKET_LEN`, the rehash hysteresis, the
small-`n` fallback threshold, and NUMA first-touch. All guesses until profiled.

Also noted, not scheduled: `pclmulqdq` is GF(2)-linear, so at `W = 1` a whole
128-bit key hashes in ~2 instructions — but hashing is off the hot path (§2.6),
so this only helps ingestion and rehash. And the gather loop is the natural home
for a batched `Channel` entry point (SIMD, GPU), which §5's scalar
one-term-at-a-time `apply` could not express.

## 8. Truncation

§7's split is unchanged: a hot per-output `keep_term`, and a per-layer
`finalize_layer` that may be non-local. `keep_term` is still applied to the
**summed** coefficient inside the merge, preserving the documented semantics and
the `threshold_applied_after_summation` test.

`finalize_layer` needs a bucketed counterpart:

```rust
fn finalize_layer_bucketed(&self, sum: &mut BucketedSum<W>) {
    // default: into_sum -> finalize_layer -> from_sum. Correct but slow;
    // keeps custom policies working unchanged.
}
```

`TopN` overrides it and becomes *cheaper* than v0.1's version, which allocates a
permutation plus three full-size gather `Vec`s and does a second `O(n log n)`
sort per layer (`truncation/builtin.rs:69-99`). Bucketed: gather magnitudes,
`select_nth_unstable` once for a global threshold, then filter each bucket in
parallel. Per-bucket filtering preserves within-bucket order automatically, so
`top_n_preserves_sort_order` still holds. `CoefficientThreshold`, `WeightCutoff`
and `Or` are no-ops here as they are today; `And` recurses.

## 9. Determinism and verification

### 9.1 Determinism

v0.1 guarantees byte-identical output across thread counts
(`sort_merge.rs:557`). v0.2 **strengthens** this to byte-identical across thread
counts *and* across bucket counts `B`, which matters because `B` now changes
mid-run via `rebucket`.

Three mechanisms:

1. Bucket tasks write only their own bucket, so no interleaving is observable.
2. The within-bucket sort is stable.
3. Delta entries are iterated in a canonical order keyed on the **local delta
   `d`**, never on `δ = H·d` — because `δ` depends on `B` while `d` does not.
   Groups are ordered by their minimum member `d`, members within a group by `d`.

Point 3 is the subtle one: floating-point summation is non-associative, so the
order in which duplicate keys are accumulated is observable, and the naive
implementation (iterate `groups` in construction order) would make results depend
on `B`.

### 9.2 Verification

The v0.1 engine is retained as a **differential-testing oracle**: a property test
asserting that `apply_layer_bucketed` and `sort_merge::apply_layer` agree, over
random sums × every channel × every policy. For a rewrite of the Pauli algebra's
hot path this is the cheapest available correctness net, and it is why §6 keeps
`apply` alongside `prepare`.

A second oracle covers §5.3: every built-in's derived local PTM must reproduce
its `apply` on randomized full-width inputs, which is what catches a channel
peeking outside its declared support.

End-to-end, `examples/ising_2d_quench.rs` must reproduce the committed
`examples/output/ising_{4x4,6x6}.csv` to floating-point tolerance — 4320 layers
of real propagation with truncation active, the strongest whole-system signal in
the repo.

## 10. GPU and distributed readiness

§10's argument is unaffected in substance and improves in two places.

The per-bucket owned columns of §4.2 are a departure from "each `Vec` maps
directly to a device buffer"; a flat SoA-plus-offsets form is recoverable in one
pass, and is the natural upload shape — one block per bucket, gather and sort in
shared memory, which is a better fit for CUB than v0.1's global sort was.

More importantly, §12's remark that the design "extends naturally to distributed
execution via a partitioning scheme on the high-order key bits" now has a
concrete mechanism, and a better one: partition on `h` rather than on key bits.
By §2.4 a rank-`r` channel makes each output bucket depend on `2^r ≤ 16` input
buckets, so a distributed layer is a sparse, statically-known, small-fan-in
exchange — and by §2.5 no key is ever split across ranks, so no rank needs to
reduce against another. Key-bit partitioning gives neither property (§3.2).

## 11. Open questions

1. **The §7.1 amplitude-representation split.** Whether `Phase`/`f64`/`Complex64`
   variants earn their complexity, or whether one `Complex64` path is enough.
2. **§7.2 vs §7.3 vs plain sort** for the within-bucket step. All three are
   `O(m)`-ish with different constants; the answer is likely workload-dependent
   (Clifford-heavy vs rotation-heavy vs noisy), which would argue for choosing
   per prepared channel rather than globally.
3. **Rehash policy.** Whether hysteresis bands are enough, or whether `rebucket`
   should be amortized incrementally across layers rather than done in one pass.
4. **`H` per sum vs per process.** Per-sum is more flexible; per-process makes any
   two sums combinable. Currently per-sum, seeded reproducibly.
5. **Whether `BucketedSum` should be public.** Exposing it lets a caller stay
   bucketed across many `propagate` calls and avoid re-conversion; keeping it
   internal keeps the public surface at §3.2's one sum type.
