# v0.6 gather/merge optimizations: measured results

Host: ccqlin038 (2× Xeon Gold 6244, 16c/32t, 2 NUMA nodes, shared box —
load from interactive tooling only, noted per campaign). rustc 1.94.0.
Baseline for every comparison:
`benchmarks/results/2026-08-30-ccqlin038/v05-S2.{json,-probe.json}`.
Campaigns in `benchmarks/results/2026-08-31-ccqlin038/`: `v06-G1`
(pure borrow), `v06-G1M1` (borrow + segment merge), `v06-G1b` (+`-r2`
repeat probe; density hybrid), `v06-G1c` (hybrid + split run loops),
`v06-G1d-ab-*` (coefficient-only materialization, interleaved A/B — the
landed form). Plan:
`research/plans/2026-08-31-v0.6-gather-merge.md`.

Headline: **G1 as planned (recompute-in-merge borrow) and M1 (segment
merge) are both negative results** — the borrow's modeled DRAM cut is real
but is paid back as per-row transform cost relocated into the merge's
serial compare loop, and the segment machinery loses on the workloads' id/
rest densities. What survived is **G1d**: keep v0.5's gather structure but
materialize only the 16-byte coefficient for a *dense* identity stream
(rotations, general unitaries), borrowing the key columns from the source
bucket — no arithmetic added to the merge, no duplicate `commutes_with`,
2/3 of the id-traffic saving. The plan's §5 gates were not met by any
variant.

## G1 as planned (pure borrow) — mixed, not kept as-is (`v06-G1`)

Dropping the materialized `id_*` columns entirely and borrowing the source
bucket in the merge, with an `Fn(usize) -> Option<Complex64>` per-row
coefficient transform (`None` = zero-amplitude skip):

Probe wall ms/layer vs v05-S2 (n=10⁶, W=2):

| cell | 1t | 16t | 32t |
|---|---|---|---|
| trotter | 79.6 (−1.9%) | 10.9 (−2.1%) | 8.86 (**−10.0%**) |
| rotation_zz | 47.4 (+0.1%) | 3.87 (+3.7%) | 3.30 (−3.9%) |
| gu2q | 137.3 (−3.5%) | 14.4 (**−11.0%**) | 12.3 (−6.3%) |
| cnot | 51.9 (**+23.7%**) | 5.57 (**+29.4%**) | 3.41 (**+15.1%**) |

Criterion: gu2q −7.8%, rotation_w4 −6.4% — but cnot **+22.1%**,
clifford1q_h **+15.9%**, rotation_zz +5.8%.

The row counters pin the cnot/h failure exactly: v0.5's materialized id
stream was *pre-filtered* — zero-amplitude rows never entered it — while
the borrowed stream is the whole source bucket. cnot's merge a-scan went
248,810 → 1,000,000 rows/layer (id amp nonzero on 4 of 16 support
patterns; h: 2 of 4), each scanned row paying a key compare +
`support_bits` + amp lookup + skip branch. Where the id stream is dense
(rotations, gu2q: every source row emits an id row) the scan length is
unchanged and the traffic cut shows — but only at high thread counts, and
merge busy still rises ~28% at 1t from the in-loop transform
(rotation_zz 19.0 → 24.4 CPU-ms/layer).

## M1 (segment-copy merge) — negative result, reverted (`v06-G1M1`)

Restructured `merge2_into` into: gallop to the next rest key, bulk-process
the id segment between (`extend_from_slice` keys + coefficient-only loop
with in-place compaction), general seed-and-extend only on keys present in
the rest stream. Measured on top of G1, merge busy CPU-ms/layer at 1t:

| cell | G1 merge | G1+M1 merge | wall Δ vs v05 |
|---|---|---|---|
| cnot | 23.3 | 28.5 | +36.3% |
| rotation_zz | 24.4 | 31.2 | +16.2% |
| gu2q | 50.4 | 68.3 | +10.4% |
| trotter | 39.7 | 36.9 | −3.8% |

Cause: the real workloads' id/rest row ratios (rotation ~1.5, cnot ~1.3,
gu2q ~0.4 — rest *denser* than id) make the average id segment a row or
two, or empty. Per-segment gallop calls and tiny `extend_from_slice`s cost
more than the per-row compares they avoid. Only trotter (~6 rows/segment,
commuting-heavy) saw a small 1t win, and it inverted at 32t. Recorded in a
comment at the merge loop; don't reintroduce without a workload whose rest
stream is far sparser than trotter's.

## Recompute-borrow repairs that did not clear the bar (`v06-G1b`, `v06-G1c`)

Two repairs on the recompute-in-merge formulation, both driven by the
measurements above:

1. **Borrow only a dense identity** (id amplitude nonzero for every active
   support pattern — rotations and `GeneralUnitary1Q/2Q` yes, Cliffords
   no). This restored cnot/h to baseline (±3% in every later run) and is
   kept in G1d.
2. **One specialized run loop per plan variant** (`v06-G1c`) to chase a
   ~4–7% 1t rotation/trotter regression `v06-G1b` showed versus `v06-G1`
   on code-identical paths. It did not recover it (rotation_zz 1t 50.3 vs
   G1's 47.4), and the cross-campaign behavior of *untouched* code
   (depolarizing: −12%…+5% between campaigns, criterion −1.5%…+5.0%)
   showed the box's single-shot noise floor is ~±5–8% at 1t and
   ~±10–26% at 8t/32t (bracketed by the same-binary repeat pair
   `v06-G1b`/`-r2`). Conclusion: the recompute-borrow family is at best a
   wash outside gu2q, its one solid cost is +~30% merge busy on the
   rotation family (present in all three builds), and effects this size
   need interleaved A/B measurement, not one campaign per build.

## G1d — coefficient-only materialization (the surviving variant)

The G1/M1 dichotomy — materialize 48 B/row vs materialize nothing and
recompute in the merge — was a false one. G1d keeps v0.5's gather
structure (transform computed once, in the high-ILP gather loop, zero
arithmetic added to the merge) but for a **dense** identity stream writes
only the 16-byte coefficient into `id_coeff`, aligned 1:1 with the source
bucket, whose key columns the merge borrows in place. Per dense id row:
80 B of run traffic (write+read of key+coeff) drops to 32 B; nothing else
changes. Sparse (Clifford) plans keep the full v0.5 pre-filtered
materialization. Output stays bitwise identical to v0.5 (same
coefficients computed in the same order; fingerprint net untouched).

Measured with an interleaved A/B protocol (same-session alternation of
two prebuilt probe binaries, order base,g1d,g1d,base,base,g1d — adjacent
in time, ~90 s total, so drift within a pair is negligible; 12 cells:
rotation_zz/cnot/gu2q/trotter × 1,16,32 threads; raw JSON per run in
`v06-G1d-ab-{base,g1d}-r{1,2,3}.json`, protocol log `v06-G1d-ab.log`).
Per-pair Δ% (g1d vs base), all three pairs listed:

| cell | t | pair Δ%s | mean | direction |
|---|---|---|---|---|
| rotation_zz | 1 | −9.6 / −11.0 / −11.8 | **−10.8%** | consistent |
| trotter | 1 | −8.0 / −8.3 / −8.6 | **−8.3%** | consistent |
| gu2q | 1 | −4.5 / −3.7 / −5.4 | **−4.5%** | consistent |
| gu2q | 16 | −15.3 / −6.2 / −5.9 | **−9.1%** | consistent |
| gu2q | 32 | −6.0 / −1.8 / −2.3 | **−3.4%** | consistent |
| cnot | 1 | −4.4 / −2.3 / −4.2 | **−3.6%** | consistent |
| rotation_zz | 32 | −10.6 / +1.3 / −5.8 | −5.1% | mixed |
| rotation_zz | 16 | +22.4 / −26.3 / −7.4 | −3.7% | mixed |
| trotter | 16/32 | — | +2.2% / +1.4% | mixed |
| cnot | 16/32 | — | −0.9% / −1.7% | mixed |

Mechanism confirmed by the 1t busy phases (mean over runs): merge
19.3 → 16.8 CPU-ms/layer on rotation_zz (−12.7%) and 34.5 → 29.2 on
trotter (−15.3%) from reading 16-byte coefficients instead of 48-byte id
rows; gather −7.5% / −3.7% from writing a third of the bytes; even the
sort improves a few percent (less cache pressure from the run's id
columns). Nothing pays anything back — unlike the recompute variants, no
arithmetic moved into the merge.

**Kept.** Six cells consistently faster across every pair — including the
two 1t cells the recompute borrow could never win — and no consistent
regression anywhere. The high-thread-count cells are flat: the hoped-for
bandwidth-wall payoff at 32t did not materialize (trotter 32t mean +1.4%,
mixed), so G1d's win is a working-set/traffic win that shows at 1–16t,
not a memory-wall breakthrough.

## Cumulative and gates

The plan §5 gates (trotter 32t < 8 ms/layer, rotation_zz 32t < 3.0 ms)
were **not met by any variant**: best measured trotter 32t 8.70–9.48 ms,
rotation_zz 3.30–3.86 ms. The modeled `2×id×T` DRAM cut overestimated the
win: the borrowed re-read is only partly cache-resident, and (in the
recompute variants) the per-row transform moved from the parallel,
prefetch-friendly gather into the merge's serially-dependent compare
loop, where the same operations cost ~2–3× more and inflate further under
SMT at 32t.

## G2 — interleaved transient key layout: negative result, not landed

Attempted on top of G1d: the run's rest-stream keys stored as one
contiguous `[[u64; W]; 2]` (`[x-words, z-words]`, derived `Ord` = the
same lex order) instead of separate `x`/`z` columns; sparse id columns
and the `PauliSum` destination stayed SoA. Measured with the same
interleaved A/B protocol (3 pairs, baseline = landed G1d HEAD;
`v06-G2-ab-*.json`, log `v06-G2-ab.log`):

- **gu2q, the gate cell (needed −10%): +1.9% at 1t (consistent),
  −2.8% at 32t.** Its sort — the phase G2 targeted — got *slower*
  (+8.4% busy at 1t): the SoA comparator usually decided on the x words
  alone and only touched z on a tie, so halving the "streams" mostly
  doubled the bytes per compare probe; only the gather's scatter won
  (−4.8%).
- **Consistent regressions where the borrowed id stream dominates:**
  rotation_zz +17.1% at 16t / +9.7% at 32t, trotter 1t +5.9% (merge busy
  +9–15%). With G1d's borrow, the merge's a-side is SoA and the b-side
  interleaved: every compare straddles both layouts and every a-row take
  repacks `[a_x[i], a_z[i]]` into a fresh interleaved key before the
  final SoA split into `dst`.
- cnot's sort improved (−13.9% busy; only ~−2.6% wall at 1t) — the one
  cell where the layout paid, and not nearly enough.

Reverted per the plan's own gate ("if gu2q doesn't move, don't land
it"). If revisited, it only makes sense **jointly** with an interleaved
a-side — i.e. abandoning G1d's SoA borrow — which the G1d numbers say
costs more than G2 could recover.
