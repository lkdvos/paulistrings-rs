# v0.1 baselines — extended surface

*2026-08-26. Slice A.2 of `research/plans/2026-08-26-v0.2-tdd-slices.md`. Host and
caveats as in `2026-08-26-v0.1-baselines.md` (unpinned `powersave` governor; ~5%
run-to-run noise floor, measured — `pauli_sum_add/1e6` moved 19.98 → 19.02 ms
between two back-to-back runs of identical code). Raw output:
`benchmarks/results/2026-08-26-ccqlin038/criterion-extended-raw.txt`.*

All figures are criterion medians. `W = 2`, 128 qubits, `AlwaysKeep` policy
(so truncation is not in the timed path).

## 1. Layer cost is independent of the channel

`apply_layer` at n = 10⁶, monomorphized:

| channel | class | time | vs. `pauli_sum_add` (19.0 ms) |
|---|---|---|---|
| `Depolarizing` | keys **unchanged**, coeff rescale | 60.8 ms | 3.2× |
| `Clifford1Q::h` | key **bijection**, fanout 1 | 60.3 ms | 3.2× |
| `Clifford2Q::cnot` | key bijection on 2 qubits, fanout 1 | 61.2 ms | 3.2× |
| `PauliRotation(ZZ)` | fanout 2, **non-injective** | 191.5 ms | 10.1× |

The first three are **identical within noise**. That is the central finding of
this baseline: a `Depolarizing` layer only multiplies each coefficient by a
scalar — keys come out bitwise unchanged, so the output is *already* sorted and
duplicate-free — and it costs the same as a two-qubit Clifford conjugation. The
channel's own work is not measurable. Layer cost is essentially all engine
overhead: three zero-filled `n × max_fanout` scratch buffers, the sequential
`sort_phase`, and its second full materialization of the payload.

`PauliRotation` costs 3.2× the Cliffords because fanout 2 produces ~1.5×10⁶
outputs to sort rather than 10⁶, and is the only case where the merge phase has
real duplicates to combine.

## 2. Thread scaling — the serial fraction

One `PauliRotation(ZZ)` layer at n = 10⁶, under explicit
`rayon::ThreadPoolBuilder` pools:

| threads | time | speedup |
|---|---|---|
| 1 | 237.98 ms | 1.00× |
| 2 | 214.81 ms | 1.11× |
| 4 | 195.86 ms | 1.21× |
| 8 | 190.75 ms | 1.25× |
| 16 | 180.90 ms | **1.32×** |
| 32 | 192.57 ms | 1.24× |

**32× the threads buys 1.32×, and 32 threads is slower than 16.**

Inverting Amdahl at p = 16 (`S = 1/(s + (1−s)/p)`, `S = 1.316`) gives a serial
fraction of **s ≈ 0.74**: roughly three-quarters of a layer runs on one core.
That is `sort_phase` (`sort_merge.rs:215`) plus the sequential
`compact_in_place` (`:146`) and the final chunk concatenation (`:326`).

v0.1 scope §9 claims this pattern gives "near-linear scaling up to the memory
bandwidth limit". It is off by a factor of ~24. The regression at 32 threads is
consistent with the host's 2 NUMA nodes plus hyperthreading on a
memory-bound parallel section.

Read the other way, this is the size of the v0.2 prize: only ~26% of the layer is
currently parallel, so eliminating the serial sort is worth up to ~3.8× *before*
any scaling improvement, and it is what makes scaling possible at all.

## 3. Dynamic dispatch is NOT a significant cost

`propagate` erases channels to `&dyn Channel<W>` (`engine/mod.rs:78`), so every
real layer pays a vtable call per input term, while the v0.1 bench passed the
channel concretely and devirtualized. Measuring both:

| channel | mono | `dyn` | overhead |
|---|---|---|---|
| `Depolarizing` | 60.82 ms | 61.66 ms | +1.4% |
| `Clifford1Q::h` | 60.35 ms | 62.43 ms | +3.4% |
| `Clifford2Q::cnot` | 61.22 ms | 61.67 ms | +0.7% |
| `PauliRotation(ZZ)` | 191.54 ms | 197.28 ms | +3.0% |

**1–3% at n = 10⁶**, i.e. at or barely above the noise floor. This **corrects a
prior assumption**: the v0.2 planning notes listed "a vtable call per input term"
as a meaningful cost alongside the sort. It is not. Hoisting dispatch to
per-layer is still worth doing — it comes free with the prepared-channel form
(v0.2 §5) — but it must not be advertised as a source of speedup.

(The n = 10⁴ figures showed up to +14%, but at 10⁴ the whole measurement is
within the noise band and the ordering is not stable across runs. Ignore them.)

## 4. Occupancy: the realistic regime is cheaper than the synthetic one

`PauliRotation(ZZ)` on qubits (0,1), n requested = 10⁶:

| input | realized n | time |
|---|---|---|
| dense (all 128 bits random) | 1 000 000 | 186.66 ms |
| weight 8 | 1 000 000 | 127.53 ms |
| weight 4 | 999 330 | 113.00 ms |
| weight 2 | **73 535** | 7.05 ms |

Every pre-existing bench used *dense* random Paulis, which is the opposite of the
physical regime — real Hamiltonians are low-weight and `WeightCutoff` keeps them
that way. Low-weight input is 1.5–1.65× cheaper at comparable `n`, because a
weight-`w` string over 128 qubits only touches the generator's support with
probability ≈ `2w/128`, so it mostly *commutes* and the realized fanout is near 1
instead of ~1.5.

**Caveat on the weight-2 row:** weight-2 strings over 128 qubits have only
`C(128,2)·9 ≈ 73k` distinct keys, so the accumulator deduplicated 10⁶ requests
down to 73 535 and that row is not comparable at fixed `n`. It is kept because it
is the saturation case, not because it is a speed result.

This is also the regime that decides bucket load balance (v0.2 §3.2), and the
reason `H` must be dense and random rather than a coordinate projection: on these
inputs the selected key coordinates are almost always zero.

## 5. Multi-layer `propagate`

A 1-D transverse-field Ising Trotter step on 32 qubits — 32 ZZ bond rotations
then 32 single-site X rotations, 64 channels, `W = 1`, no truncation:

| starting n | time |
|---|---|
| 1 000 | 136.97 ms |
| 10 000 | 863.80 ms |

With `AlwaysKeep` the sum grows through the circuit, so this measures early
growth rather than steady state — the steady-state number is the Ising example in
`2026-08-26-v0.1-baselines.md` (4×4 = 21.2 s, 6×6 = 136.1 s). Included because no
prior bench exercised the multi-channel call shape at all, and per-layer fixed
costs are multiplied by 64–108 in any real circuit.

| target | baseline |
|---|---|
| Clifford layer, 10⁶, 32 threads | 60.3 ms (15.8 Melem/s) |
| Rotation layer, 10⁶, 32 threads | 191.5 ms |
| Rotation layer, 10⁶, 1 thread | 238.0 ms |
| Best parallel speedup, any thread count | **1.32×** |
| Serial fraction | **~74%** |
| Ising 6×6 quench, 4320 layers | 136.1 s |

And the reference floor for "what a linear pass over this payload costs":
`pauli_sum_add` at 10⁶ = 19.0 ms, 100 Melem/s.
